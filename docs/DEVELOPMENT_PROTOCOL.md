# 調唱統一開發流程

- 文件版本：1.1
- 生效日期：2026-08-21
- 適用對象：人類工程師、Gemini、Codex 與其他協作 AI
- 目的：建立「極簡 Token 消耗」與「先立檢驗標靶再撰寫程式碼」的標準化開發驗證紀律

---

## 0. 核心紀律：Token 最佳化與避免先射箭再畫靶

在 AI 協作開發中，反覆閱讀與生成長篇 Markdown 文件會消耗大量 Token 與時間。本專案嚴格遵循以下兩大運作準則：

### 準則 A：既有功能優先採用「標準化檢驗程序」（以程式 LOG 代替文字推論）
1. **程式化客觀證明**：只要是原本已設定、未修改的既有功能，進行回歸檢查時**一律優先執行標準化檢驗腳本**（`pnpm run check`）。
2. **LOG 取代反覆閱讀**：由程式直接產出確定性、結構化的簡要 PASS/FAIL LOG，不再依據大量 MD 文件反覆逐條推敲，大幅節省 Token 並杜絕人工幻覺。

### 準則 B：新功能採用「先立標靶，再寫程式碼」（Test-First / Verification-First）
1. **步驟一（立靶）**：在撰寫任何業務程式碼前，**必須先定義好這項新功能打算如何被客觀檢驗**（例如：新增單元測試案例、設定可重現的輸入／預期輸出斷言、或建立端到端驗證情境）。
2. **步驟二（射箭）**：依據預先設定的標靶規範，進行最小範圍的程式碼開發與調整。
3. **步驟三（驗收）**：直接以步驟一預先設定的檢驗方式執行驗證。
4. **禁止先射箭再畫靶**：嚴禁「先寫完代碼，再事後反向編造測試或模糊標準來湊出成功」的不良慣性。

## 1. 唯一真實來源

每一項工作都必須同時對照以下文件：

1. `docs/PROJECT_SPEC.md`：產品目標、範圍與驗收標準。
2. `TODO.md`：目前優先順序與待辦狀態。
3. `docs/DEVELOPMENT_LOG.md`：已完成的變更與實際驗證證據。
4. `docs/ARCHITECTURE_DECISIONS.md`：不可任意推翻的技術決策。
5. `docs/TESTING.md`：可重跑的測試步驟。

若程式、README、TODO 與開發紀錄互相矛盾，先標記為「文件不同步」，不得直接宣稱功能完成。

## 2. 任務生命週期

### 2.1 任務開始前：Ready（先立標靶）

開始寫程式前，必須先明確：

- 使用者問題與目標。
- 不包含的範圍。
- 影響的資料模型、協定、UI、權限與外部服務。
- **預先定義的檢驗方式（Test Plan / Predefined Assertions）與可觀察的成功標準**。
- 可能的安全、著作權、效能與瀏覽器相容性風險。

### 2.2 實作中：小步驟與可回復（精準射箭）

- 先閱讀相關檔案與現有測試，再修改最小必要範圍。
- 協定、資料模型與儲存格式的變更要先更新型別，再更新背景、UI 與預覽層。
- 不用隨機值、假延遲或靜態成功訊息冒充真實演算法。
- 暫時無法完成的功能要顯示 `experimental` 或 `not implemented`，並記錄原因。
- 外部網站解析、AI、DSP 與權限流程都要有失敗路徑，不可只處理成功情境。
- 不刪除使用者資料、舊發布包或其他工具的工作成果，除非任務明確授權。

### 2.3 完成前：Done（嚴格中靶檢驗）

功能只有在以下條件全部成立時才能標記完成：

- 以步驟 2.1 預設的檢驗方式執行，結果完全符合預期。
- 執行標準化全流程檢查 `pnpm run check`（型別檢查、單元測試、正式建置、DSP 準確度與端到端煙霧測試）全部 PASS。
- 正常、空資料、錯誤、取消與重新載入情境都有處理。
- 文件、版本號、權限說明與實際行為一致。
- 簡要記錄變更、驗證命令、LOG 結果、未完成風險與下一步。

## 3. 固定標準化檢驗層級

每次提交依序執行：

```bash
pnpm run typecheck
pnpm test
pnpm run build
pnpm run test:pitch
pnpm run test:extension
pnpm run package
```

`pnpm run check` 是上述核心檢查的快速整合入口。若某一項不能執行，必須在開發紀錄明確寫出原因與替代證據。

### 必要測試內容

- DSP：十二平均律、cents、速度、Varispeed、音訊延遲與音高誤差。
- BPM：固定節拍、半速／雙速、無節奏與短音訊失敗情境。
- 歌詞：LRC／SRT／VTT／TXT、逐句編輯、打拍、Lead Time、匯出與復原。
- 播放：同一分頁切歌、單曲循環、歌單下一首、A–B、取消與重新載入。
- 儲存：本機資料、Chrome Sync、離線、配額與資料格式升級。
- UI：亮／暗主題、四語言、320 × 900 與 420 × 900、不溢出、不阻塞捲動。
- AI／外部服務：無效 Key、拒絕權限、網路失敗、超過大小上限與使用者取消。

## 4. AI 與外部服務規則

- API Key、Cookie、Token、個人歌詞與測試音訊不得寫入原始碼、測試快照、README、ZIP 或網站。
- 個人測試 Key 可以由使用者在 UI 輸入後保存於本機 `chrome.storage.local`，但不得有預設值，也不得進入公開發布包。
- 發布前必須掃描：`gsk_`、`sk-`、`AIza`、`AKIA`、私密 URL 與個人資料。
- Groq 是選用外部服務；只有使用者明確按下產生並同意後才能傳送音訊。
- YouTube 串流解析依賴非公開資料時，必須標記相容性風險，不得宣稱「永遠有效」或「100% 免疫」。
- 受著作權保護的完整歌詞不自動抓取、不內建、不散布；只處理使用者有權使用的內容。

## 5. 音訊與人聲分離決策流程

人聲功能分三層驗證，不可把其中一層誤稱為另一層：

1. 即時 Mid/Side：低延遲、完全本機，但可能一起削弱置中的鼓與 Bass。
2. 本機 AI 分離：研究 UVR／Demucs／MDX／VR 等模型，需確認模型授權、下載大小、記憶體、MPS／WebGPU 與 Chrome 相容性。
3. 雲端分離：必須明確顯示上傳、保存期限、費用、隱私與使用者同意，不能默默把串流音訊送到第三方。

每個模型候選都要用相同測試集比較：人聲殘留、伴奏失真、鼓／Bass 保留、延遲、CPU／GPU、輸出格式與取消復原。

## 6. 版本與發布規則

- 版本唯一來源是 `package.json`；`public/manifest.json`、設定頁、README、網站 badge 與發布文件必須同步。
- 版本變更後必須重新執行 `pnpm run build` 與 `pnpm run package`。
- ZIP 只能包含 `dist/` 的正式產物，不包含原始碼、文件、測試、`.map`、`.DS_Store`、Node modules 或秘密。
- `release/` 的 ZIP 時間必須晚於最後一個原始碼變更。
- 發布前至少保留一個可回復的舊 ZIP，但不得把舊版本誤標成最新版本。
- 未決定正式託管位置前，網站只維持內容與離線預覽品質，不宣稱已上線或可下載。

## 7. 交接格式

每個工程師或 AI 完成工作後，在回覆與 `DEVELOPMENT_LOG.md` 使用以下格式：

```text
任務：
使用者結果：
變更檔案：
驗證命令：
驗證結果（含程式 LOG 摘要）：
未完成／風險：
下一步：
```

下一位協作者必須先讀這段交接，再開始修改；不能只依賴聊天記憶或「看起來已完成」的 UI。

---

## 8. 官方網站內容標準

- 所有功能文案必須與實際 build 版本一致。
- 「已支援」「可用」「實驗中」「規劃中」四種狀態要分開呈現。
- 不使用無法由程式或測試證明的速度、準確度與相容性承諾。
- 先完成繁中內容、功能截圖、隱私說明、支援 FAQ 與版本資訊，再決定部署平台。
- 不在尚未決定託管位置前加入會誤導使用者的下載按鈕或正式商店連結。
